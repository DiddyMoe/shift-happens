# Commit All

## Outcome

Commit every eligible working-tree change present at invocation as Conventional Commits on the current branch, one logical change per commit, with every check under "Checks" passing. The number of commits follows from the changes; never merge unrelated work to reduce it.

Atomic means one logical change, not the smallest possible diff or a separately checked intermediate repository state. An ordered migration may span multiple commits whose final contract is established by the series. Do not manufacture prerequisite or support-only microcommits solely to make intermediate snapshots pass.

Work from the difference between `HEAD` and the working tree. Every staged file is either its working-tree content or `HEAD` plus whole, unedited hunks from `git diff`, so each commit holds only edits that exist in the tree. Keep the effort proportionate: settle the groups in one pass, then commit them.

A failing check is work to do, not a reason to stop. The run ends when every eligible change is committed and the full "Checks" sequence passes on the final tree without modifying files, or at a blocker defined under "Stop conditions".

## Checks

This repository has no Git hooks, pre-commit framework, or CI workflow. Its gates are the formatting, type, lint, build, and debug/release Clippy checks that `scripts/release-windows.ps1` runs natively on Windows, in the WSL cross-compilation form from `README.md` and `docs/technical-reference.md`, plus notices regeneration. None of them runs tests. Run them from the repository root, in this order:

```sh
npm run format:check
npm run typecheck
npm run lint
npm run rust:fmt
XWIN_CACHE_DIR="$HOME/.cache/shifthappens-xwin" XWIN_ARCH=x86_64 cargo xwin clippy --manifest-path src-tauri/Cargo.toml --locked --target x86_64-pc-windows-msvc --bins --lib -- -D warnings
npm run build
XWIN_CACHE_DIR="$HOME/.cache/shifthappens-xwin" XWIN_ARCH=x86_64 cargo xwin clippy --manifest-path src-tauri/Cargo.toml --locked --target x86_64-pc-windows-msvc --release --features tauri/custom-protocol --bins --lib -- -D warnings
npm run notices
```

On native Windows, use `npm run rust:clippy` and plain `cargo clippy` with the same arguments instead of the `cargo xwin` lines. `npm run rust:clippy` from WSL targets Linux and needs GTK development packages, so do not use it there.

Some steps rewrite files; keep their rewrites as part of the change that caused them:

- `npm run format:check` and `npm run rust:fmt` only report. Fix their findings with `npx prettier --write <reported paths>` and `cargo fmt --manifest-path src-tauri/Cargo.toml`.
- Clippy runs `src-tauri/build.rs`, which regenerates `src-tauri/permissions/autogenerated/` from the command list.
- `npm run build` runs `scripts/sync-version.mjs`, which rewrites the version in `src-tauri/Cargo.toml` and `src-tauri/Cargo.lock` when it drifts from `package.json`.
- `npm run notices` regenerates `src/generated/third-party-notices.txt` from the dependency graph. That file is derived; it belongs to the commit that changes dependencies, the generator, or `scripts/notice-supplements/`.

A full pass means every step exits zero and `git status` shows no file the sequence changed. `dist/` is ignored build output.

AGENTS.md requires inspecting a script's definition before running it. Confirm the `package.json` scripts still match the list above, and re-inspect any script, configuration file, or `src-tauri/build.rs` that the inventoried changes modify before running checks over them. Never add a test command to this sequence.

## Commit boundaries

A logical change is one reason to change the code: one fix, feature, refactor, or migration that can be described, reviewed, and reverted on its own.

Split a group when any of these holds and whole files or whole hunks separate it:

- its subject needs "and" or a comma list to describe it;
- its body needs separate paragraphs for unrelated topics;
- it fits more than one Conventional Commit type;
- it mixes refactor, rename, move, or formatting hunks with behavior changes.

Keep together:

- a change and its callers, the `README.md` or `docs/technical-reference.md` sections that document it, its configuration, and the derived files that checks regenerate;
- one mechanical change across many files, such as a rename or a tool-applied rewrite, regardless of size;
- a coordinated breaking migration whose parts do not work apart;
- a Tauri command change and its registration in `src-tauri/src/commands.rs`, `src-tauri/build.rs`, `src-tauri/capabilities/main.json`, and `src-tauri/permissions/autogenerated/`.

Split at file level first, and at whole-hunk level only when the separation is clear and safe. Never split inside a hunk, edit a hunk, or write file content that exists in neither `HEAD` nor the working tree. When intents interleave in a file so that whole hunks cannot separate them, keep that file's changes in one commit and name the carried change in the body. `docs/technical-reference.md` is long and often carries hunks for several groups; split it by whole hunks where they map cleanly.

Group by evident intent. Audit reports, prompt sets, plans, logs, and verdicts, such as `AUDIT_REPORT.txt` and anything under `prompts/`, are separate from the project. They may help explain a change's intent, but they never set commit boundaries, never split a file or hunk by the findings they list, and never supply IDs or wording for a message. Leave them uncommitted unless the user names them.

Treat a group above about 1,000 changed lines as a reason to recheck it against these criteria, not as a limit.

## Commit messages

The existing history predates this convention; do not copy its style. Write each message from the staged diff:

- Header: `type(scope): subject`, at most 72 characters. Types: `feat`, `fix`, `perf`, `refactor`, `style` (formatting only), `docs`, `build` (build scripts, dependencies, versions, third-party notices), `ci`, `chore`, `revert`. The scope is optional: one short lowercase area such as `schedule`, `availability`, `employees`, `holidays`, `coverage`, `backup`, `restore`, `export`, `db`, `ui`, or `deps`.
- Subject: imperative mood, lowercase first word, no trailing period.
- Body, when the reason, a tradeoff, a carried change, or a repair is not obvious: one blank line after the header, wrapped at 72 columns, explaining why rather than restating the diff.
- A breaking change to stored data, exports, or backup/restore compatibility takes `!` after the type or scope and a `BREAKING CHANGE:` footer.

Report only checks this run performed. Do not copy earlier measurements or timings, and do not claim tests ran.

## Authority

Explicit invocation authorizes inspection, staging, commit creation, and repair of every failure that the checks or Git report during the run. Repairs may change code, documentation, configuration, and generated files, and may fix pre-existing problems those checks expose outside the inventoried changes. Make each repair under `AGENTS.md`: fix the root cause, update affected callers and documentation (`README.md`, `docs/technical-reference.md`) together, and decide intended behavior from the change, `docs/technical-reference.md`, and repository evidence without asking. Verify behavioral repairs directly as `AGENTS.md` requires; never create, modify, or run tests.

Invocation does not authorize weakening a check to force a pass:

- no `--no-verify`, and no edits to `package.json` scripts, `eslint.config.js`, `.prettierrc.json`, `.prettierignore`, `tsconfig*.json`, Rust lint settings, or the commands above that remove, narrow, or retarget what a check covers;
- no blanket or unjustified suppression (`eslint-disable`, `@ts-ignore`, `@ts-expect-error`, `prettier-ignore`, `#[allow(...)]`, `#[expect(...)]`, new ignore entries). A narrow, rule-specific suppression is acceptable only when the flagged code is correct and cannot be expressed otherwise; give the reason beside it and in the commit body;
- no loosened thresholds such as dropping `--max-warnings 0` or `-D warnings`.

A check that is itself defective may be fixed in its own commit when evidence shows the defect; the fixed check must still check what it is meant to check.

Invocation also does not authorize dependency additions, removals, or upgrades; application version or schema/migration version changes; history rewriting (reset, amend, rebase, or rewriting created commits); branch changes; push; publication; or committing secrets. Version synchronization by `npm run build` and notices regeneration for already-declared dependencies are in scope. Exclude secrets, signing material (`*.pfx`, `*.p12`, `*.pem`, `*.key`), SQLite databases and their sidecars, exports, backups, accidental binaries, caches, temporary evidence, and artifacts repository policy does not version. Treat existing staging as input, not as a commit boundary.

## Workflow

1. Inventory branch/upstream, complete status and diff, and untracked files. Require an attached branch with no active sequencer or unmerged entries; otherwise stop.
2. Group changes by evident intent, provenance, and coupling under "Commit boundaries", reading `git status` and `git diff HEAD`. Regroup when a check or repair reveals a better boundary. Do not reconstruct earlier tree states from baselines, snapshots, backups, or session records; map hunks to audit findings; build a dependency graph, exact-diff ledger, or candidate manifest; or write staging programs or plan, state, or hunk-map files. A short list of groups and their paths is enough, and `git status` shows what remains.
3. Run the "Checks" sequence. Keep the formatter and generator rewrites it applies. For each failure, repair the root cause, then rerun that check alone until it passes. When every failing check passes alone, rerun the full sequence; repeat until a full run passes without modifying files. Assign each repair to the group whose change caused the failure; give repairs of pre-existing problems their own commit.
4. For each group, stage only explicit paths or hunks: whole files with `git add -- <path>`, and a subset of hunks with `git apply --cached` on unedited hunks from `git diff`. Never write index entries directly (`git update-index --cacheinfo` or `--index-info`); `git add -N` for a new file is fine. Never use `git add .`, `git add -A`, an unscoped `git add -u`, or a repository-root pathspec. Stage in full every file a check rewrote, including `src/generated/third-party-notices.txt`, `src-tauri/permissions/autogenerated/`, and synchronized Cargo version fields. Inspect staged names and content, run `git diff --cached --check`, then commit with a message written under "Commit messages". Name any repairs in the commit body.
5. When `git commit` fails, inspect its output, fix the cause within this skill's authority, and retry. A failure outside that authority, such as missing identity or signing configuration, is a blocker.
6. Reinspect status after each commit. Your repairs and check rewrites are expected; if other edits appear concurrently, stop rather than trying to bind or reconstruct their byte history.
7. If a repair or a newly tracked file postdates the last full pass, run the sequence again on the final tree. Commit further repairs or generator rewrites as new commits; never amend. Excluded untracked files can still affect `format:check` and `lint`; if one does, report it rather than committing it.

The checks read the working tree, not the index, so they validate the final tree, not each intermediate commit. Do not check out, stash, or isolate intermediate commits to check them separately.

## Recoverable failures

- **Environment:** when `node_modules` is missing or stale, run `npm ci --ignore-scripts` and confirm `package-lock.json` is unchanged. When the Windows Rust target is missing, run `rustup target add x86_64-pc-windows-msvc`. The first `cargo xwin` run downloads Microsoft's SDK into `XWIN_CACHE_DIR` and needs network access. If sandbox capability alone blocks a check, rerun it with authorized capability.
- **Build lock:** when Cargo waits on a build-directory lock held by another process, such as a running `tauri dev`, wait for it; do not kill processes you did not start.
- **Boundary problem:** regroup and continue; do not create recursive prerequisite commits.

## Stop conditions

Besides the precondition and concurrent-edit stops in steps 1 and 6, stop only when:

- a repair needs authority this skill withholds, including an exposed secret or private key (exclude that change and report it; never commit, suppress, or rewrite it);
- an environmental failure persists after the environment is restored (network, system tool, hardware);
- the same failure recurs after three distinct root-cause repair attempts, including oscillation between two failures.

Before stopping, commit the groups the blocker does not affect, keep correct repairs in place, leave blocked changes uncommitted, and record the exact blocker with its command output.

## Completion

Inspect final status and the new commit range. Report each commit with hash, message, and intent; the repairs made and why; the final "Checks" result; exclusions; blockers; remaining changes; and what remains unverified at runtime, as `AGENTS.md` requires. A run that stops at a stop condition with exact blockers is a valid terminal outcome. Do not push.

## Claude Code execution

- Run only on explicit invocation.
- Use direct Git and the checks above. Read `AGENTS.md` and the `docs/technical-reference.md` section that governs a file before a semantic repair to it.
- Repair in the parent. Delegate only a large set of independent repairs, give each agent exclusive files and the `AGENTS.md` no-test policy, and rerun the checks yourself after integrating their edits. Do not delegate inventory, grouping, or message drafting.
- Shell state does not persist between Bash calls, so keep the `XWIN_*` assignments on each `cargo xwin` command. A cold Clippy run takes several minutes; use the 10-minute Bash timeout or `run_in_background` and wait for the exit status.
- After compaction or interruption, recover from `git status`, `git log`, and the group list.
